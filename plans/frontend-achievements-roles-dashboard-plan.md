# Plan: Achievements & Roles Web Dashboard (vanilla JS + Tailwind)

## TL;DR

**What:** Add a public web homepage to BongoBot that lists all achievements and all Discord roles, backed by a new `GET /api/achievements-and-roles` JSON endpoint, styled with Tailwind CSS.

**Why:** Surface the guild's achievement catalog and roles in a browsable web page instead of only inside Discord slash commands.

**Recommended approach:** BongoBot is already an Express HTTP app (`app.js`) — it is a *webhook-based* Discord bot (Discord POSTs interactions to `/interactions`), not a gateway/websocket process. So the web dashboard should live **in the same Express process and same `app.js`**: mount `express.static` for a new `public/` folder, add one route module for the API, and add a static `index.html` + vanilla JS that `fetch`es the endpoint. No new process, no new infra — it deploys through the existing Fly.io/Dockerfile pipeline unchanged (already `EXPOSE 3000`, `force_https`).

The achievement/role catalog already lives in importable shared modules (`roles/achievementRoles.js`, `roles/craftingRoles.js`, `roles/professionRoles.js`) — **no refactor is needed** to extract data out of command handlers. The one real gotcha is payload size: achievement icons are base64-inlined into those modules (`achievementRoles.js` alone is ~4.3 MB across 33 entries, and individual icons range from ~1.5 KB to ~735 KB). We **do** want icons shown on the page, so the fix is **not** to strip them — it is to **paginate the achievements**: `GET /api/achievements-and-roles` accepts `page`/`pageSize` query params and returns icons only for the current page's achievements, plus pagination metadata. This keeps any single response bounded (one page of icons) instead of shipping all ~4.3 MB up front. Discord roles are returned in full and are *not* paginated — see the roles note below and Decisions.

Tailwind is wired as a **Tailwind CSS v4** PostCSS build: `tailwindcss` + `@tailwindcss/postcss` devDependencies (**no `autoprefixer`** — v4 bundles vendor-prefixing and `@import` inlining), a `postcss.config.mjs` registering the `@tailwindcss/postcss` plugin, a source `input.css` whose first line is `@import "tailwindcss";` (replacing v3's three `@tailwind` directives), and a `build:css` npm script compiling to `public/dist/output.css`. A `tailwind.config.js` is **not** required in v4 — config is CSS-first via an optional `@theme { … }` block in `input.css`, which this dashboard can skip entirely unless custom design tokens are wanted.

**Real Tailwind Plus snippets are now in play — and the right package is available.** The user purchased and downloaded two Tailwind Plus packages (both outside the repo, under `~/Downloads/`): the **"Marketing"** package (`/Users/braeburn/Downloads/marketing-v4/` — heroes, footers, nav headers, marketing sections) and the **"Application UI"** package (`/Users/braeburn/Downloads/application-ui-v4/` — application shells, data-display/stats, lists/grid-lists, lists/stacked-lists, navigation/**pagination**, elements/badges, headings, feedback/empty-states). Only the `html/` variant of each is relevant (ignore `react/`, `vue/`), and both target Tailwind **v4.3** syntax — which is *why* the whole build is on v4 (v3 would silently drop/mis-render v4-only classes like `size-*`, `text-sm/6`, `inset-ring`, `not-dark:*`, `outline -outline-offset-1`). **Application UI is the correct source and is used exclusively; marketing-v4 is dropped.** App-UI is purpose-built for exactly this kind of internal dashboard and supplies a real, licensed component for *every* region the page needs — including the two the Marketing package lacked: a **grid list** for the achievement icon grid and a **real numbered pagination** component. The full outer chrome (nav header + page header + `max-w-7xl` main container) comes from a single **application shell** file, so no marketing nav/header/footer is needed. Mixing the two visual systems (marketing's landing-page scale vs. App-UI's dense gray/indigo dashboard scale) would look inconsistent, and App-UI has no `footers/` folder — but an internal admin dashboard doesn't need a marketing footer; a one-line copyright `<footer>` in the same utility classes suffices if wanted. See the snippet-sourcing section and Decisions.

## Key findings from codebase research

- **`app.js` is already an Express server.** `express@^4.18.2` is a dependency. Current routes: `GET /` (returns "IM ALIVE. STOP POKING ME."), `POST /interactions` (Discord webhook). It calls `app.listen(process.env.PORT || 3000)`. There is **no separate Discord gateway process** — interactions arrive over HTTP, so the Express server *is* the bot.
- **Discord signature verification is NOT route-scoped `verifyKeyMiddleware`, and it does NOT block the new GET routes — verified directly against the code.** The verification lives at **`app.js:16`** as `app.use(express.json({ verify: VerifyDiscordRequest(process.env.PUBLIC_KEY) }))`. `VerifyDiscordRequest` (**`discordclient.js:5-16`**) returns an `express.json` **`verify` callback** `(req, res, buf) => …` that reads `X-Signature-Ed25519` / `X-Signature-Timestamp`, calls `verifyKey(buf, signature, timestamp, PUBLIC_KEY)`, and on failure does `res.status(401).send('Bad request signature')` and throws. Two consequences:
  - It is **not** the classic route-scoped `app.post('/interactions', verifyKeyMiddleware(PUBLIC_KEY), handler)` pattern, and it is **not** a blanket rejecting `app.use(verifyKeyMiddleware(...))` that would 401 every request. It is a `verify` hook that Express **only invokes while `express.json` actually parses a request body** — i.e. only when the request has a body with `Content-Type: application/json`.
  - Although it is registered **globally** via `app.use` (every request passes *through* the middleware), a plain browser/`curl` **GET carries no JSON body**, so `express.json` is a no-op for it, the `verify` hook is never called, and no signature check runs. This is already proven in production by the existing `GET /` (`app.js:17-19`) returning 200 with no Discord headers. **Conclusion: signature verification was checked directly and the new `express.static` serving + `GET /api/achievements-and-roles` route need no middleware change — this is a confirmed non-issue, not a risk to design around.** Two guard-rails for whoever implements it: (a) mount the new static/API routes **after** `app.js:16` (as Phase 1 step 3 specifies) so they inherit the same harmless pass-through; (b) keep the new dashboard routes **GET-only** — if a future dashboard route ever accepts a JSON `POST` body it *would* be run through this `verify` hook and 401 unless signed by Discord, in which case that route needs its own body parser without the `verify` hook (or the `verify` hook must be scoped to wrap only `/interactions`). Out of scope for this GET-only feature; noted so it is not a later surprise.
- **Achievement/role data is static config in code, not Mongo.** `mongo.js` only persists *per-member* assignments (`MemberRoles`, `MemberAchievement`, `MemberApiKey`). The *catalog* is:
  - `roles/achievementRoles.js` → `ACHIEVEMENT_ROLES` (~33 objects) and `ACHIEVEMENT_CATEGORIES` (grouped, empties filtered).
  - `roles/craftingRoles.js` → `CRAFTING_ROLES`.
  - `roles/professionRoles.js` → `PROFESSION_ROLES`.
  - Each entry shape: `name` (getter = `short_name - description`), `short_name`, `description`, `custom_id`, `category` (achievements only), `color` (hex integer, e.g. `0xbf8ddc`), `icon` (base64 `data:image/png` URI, inlined via `readFileSync` at import time), `mentionable`, optional `requirements`.
- **Payload-size hazard → solved by pagination.** Icons are base64-inlined. `achievementRoles.js` ≈ 4.3 MB on disk (33 achievements; per-icon size ranges ~1.5 KB to ~735 KB); `professionRoles.js` ≈ 278 KB. Returning `icon` for *every* entry in one response yields a multi-MB JSON blob. Since the page must display icons, the API paginates achievements and only serializes `icon` for the current page's slice, bounding each response to one page's worth of icons. Note `JSON.stringify` *does* invoke the `name` getter (own enumerable accessor), so `name` serializes fine; `color` serializes as a number and needs `#rrggbb` conversion client-side.
- **Live guild roles have no base64 icons (roles stay small).** `GetGuildRoles(guildId)` (`discordclient.js:99`) returns Discord's role objects, whose `icon` field is an optional CDN **hash string or `null`** (plus optional `unicode_emoji`) — *not* an inlined base64 blob. A guild's role list is bounded by role count (tens, not thousands), so the entire `roles` array is a few KB. Only the static-catalog *fallback* (crafting/profession/achievement definition modules) carries base64 icons, so that fallback path must strip `icon`. Conclusion: **roles do not need pagination** (see Decisions).
- **"Discord roles" is ambiguous** — could mean (a) the *live* guild roles from `GetGuildRoles(guildId)` in `discordclient.js` (needs `GUILD_ID` + bot token, hits Discord REST), or (b) the managed role *definitions* (achievement + crafting + profession modules). `handleViewAchievements` in `roles/achievementHandler.js` already combines static `ACHIEVEMENT_ROLES` with live `GetGuildRoles` to resolve `role_id`. Recommendation below covers both; default is live guild roles.
- **Module system:** ESM (`"type": "module"`). `package.json` `engines.node` says 16.x but the Dockerfile pins Node 21.7.2 (use 21 as the real target).
- **No existing `public/`, `views/`, `web/`, or `dashboard/` folder.** No static serving today.
- **`.gitignore` gotcha:** line 92 is a bare `dist` pattern, which will ignore `public/dist/` (compiled CSS). Must either un-ignore it or build CSS during the Docker/Fly build. See Phase 3 / Decisions.
- **Deploy:** Fly.io, single process, `npm run start` = `node app.js`, Dockerfile `EXPOSE 3000`, `[http_service] internal_port = 3000, force_https = true`. Adding routes to the same app needs zero infra change.
- **Conventions (`AGENTS.md`):** documents Discord interaction routing only; nothing about web/static serving, so this is greenfield within the repo. Keep the existing style (ESM, small handler modules).
- **Tailwind Plus snippets downloaded (v4) — both packages explored, structure confirmed by reading files.** Two packages sit outside the repo under `~/Downloads/`: `marketing-v4/html/` and `application-ui-v4/html/`. **The dashboard is built exclusively from `application-ui-v4/html/`** (marketing-v4 dropped — see Decisions). Confirmed App-UI subfolders + chosen files (all read directly): `application-shells/stacked/01-with-bottom-border.html` (full shell: `<nav>` + `<header>` page-title band + `<main>` container), `data-display/stats/03-simple-in-cards.html` (`<dl>` summary count cards), `lists/grid-lists/06-images-with-details.html` (image + name + detail per cell → achievement icon grid), `lists/stacked-lists/17-narrow-with-badges.html` + `elements/badges/09-flat-pill.html` (role rows with colored pills), `navigation/pagination/01-card-footer-with-page-buttons.html` (real numbered pagination: Prev/Next chevrons + numbered buttons + "…" gap span + "Showing X to Y of Z results"), `feedback/empty-states/01-simple.html` (optional zero-state), with `headings/page-headings/01-with-actions.html` and `layout/cards/04-card-with-footer.html` as optional layering. All markup is Tailwind **v4.3** (verified: `size-10`, `text-sm/6`, `inset-ring inset-ring-gray-300`, `not-dark:hidden`, `outline -outline-offset-1`, `dark:*` variants) — this is why the build is v4, not v3. Two swap-out details observed: (a) all sample images point to `tailwindcss.com/plus-assets` / `images.unsplash.com` — replace the grid `<img src>` with our own base64 achievement icons and drop avatar/logo placeholders; (b) the application shell's profile dropdown + mobile menu rely on the `@tailwindplus/elements` CDN custom-elements script (`el-dropdown`, `el-disclosure`, `command="--toggle"`) — either include that `<script type="module">` or strip those interactive bits and keep the static desktop nav. Unlike the Marketing package, App-UI **does** include real list, grid, badge, and pagination components, so nothing in the core dashboard needs to be hand-built.

## Steps

### Phase 1 — Backend: shared data accessor + API route

1. **(Optional, recommended) Add a small catalog accessor module** `roles/catalog.js` that re-exports a normalized view of the three catalogs and a helper to fetch a single achievement page. It imports `ACHIEVEMENT_ROLES`/`ACHIEVEMENT_CATEGORIES`, `CRAFTING_ROLES`, `PROFESSION_ROLES` and provides:
   - A normalizer that maps each entry to a plain object `{ short_name, name, description, custom_id, category, color: '#' + color.toString(16).padStart(6,'0'), mentionable, icon }` — **keeping `icon`** (the base64 `data:` URI) so the page can render badge art. Icon size is bounded by *pagination in the route*, not by stripping here.
   - `getAchievementsPage(page, pageSize)` (or the route can do this inline): returns `{ items: normalizedSlice, total: ACHIEVEMENT_ROLES.length }`. `ACHIEVEMENT_ROLES` is a static in-memory array, so `total` is a cheap `Array.length` (O(1)) and the page is a plain `Array.prototype.slice`.
   - A `rolesForFallback()` helper that maps the static catalog modules to `{ short_name, name, color, mentionable }` **without `icon`**, used only if the live Discord roles call fails (keeps the fallback small). Gives the API and any future consumer one source of truth. Depends on: nothing (pure re-map). Parallelizable with Phase 3.

2. **Add the API route module** `routes/dashboard.js` exporting an Express `Router` (ESM). It defines `GET /api/achievements-and-roles` accepting **offset-based pagination** query params and returning JSON:
   - **Query params:** `page` (1-based, default `1`) and `pageSize` (default `12`, clamped to a sane max e.g. `50`). Parse with `Number.parseInt`, coerce invalid/negative values to defaults, and clamp `page` to `[1, totalPages]`.
   - **Slicing lives here (in the route/controller).** `total = ACHIEVEMENT_ROLES.length` (O(1)); `totalPages = Math.max(1, Math.ceil(total / pageSize))`; `start = (page - 1) * pageSize`; slice `ACHIEVEMENT_ROLES.slice(start, start + pageSize)`, then normalize **including `icon`** (via step 1's normalizer). Because `achievementRoles.js` is a static module already fully in memory, pagination is pure array slicing — no DB, no async, no cursor bookkeeping.
   - **`achievements`** response shape: `{ items: [...normalized page with icon...], pagination: { page, pageSize, total, totalPages } }`. Optionally include the achievement's `category` on each item so the client can group within a page (full `ACHIEVEMENT_CATEGORIES` grouping across all pages is not sent — grouping is per-page or dropped in the paginated design).
   - **`roles`: returned in full, NOT paginated.** **Live** Discord guild roles via `GetGuildRoles(process.env.GUILD_ID)` from `discordclient.js`, mapped to `{ id, name, color, position, managed, mentionable }` (Discord returns `color` as an int → convert to `#rrggbb`; filter out `@everyone` / `position 0` if undesired). Guild role objects have no base64 icons, so the whole array is a few KB (see Decisions for why this is not paginated). Wrap in try/catch; on Discord failure fall back to `rolesForFallback()` (icon-stripped static catalog) and/or a 502 with an error field. **Optimization:** include `roles` only when `page` is `1`/absent and omit it on subsequent "load more" pages, so achievement paging doesn't re-transmit the roles list on every fetch (the client fetches roles once on initial load). Returning `roles` on every request is an acceptable simpler alternative given the small size + cache.
   - Add a lightweight in-memory cache (e.g. 60s TTL) around `GetGuildRoles` so page refreshes / repeated achievement-page fetches don't hammer the Discord REST API. Depends on: step 1, `discordclient.js` (existing).

3. **Wire the route + static serving into `app.js`.** After the existing `app.use(express.json(...))`:
   - `app.use(express.static('public'))` (serves `index.html`, compiled CSS, and client JS).
   - `app.use(dashboardRouter)` (the new `/api/...` route). Import the router at the top of `app.js` alongside the existing imports.
   - **Middleware / Discord signature verification — no re-scoping required (confirmed against `app.js:16`).** Mount both `express.static('public')` and `dashboardRouter` **after** line 16's `app.use(express.json({ verify: VerifyDiscordRequest(...) }))`, exactly as written above; leave that line unchanged. The `verify` hook only fires while `express.json` parses a JSON body (see Key findings), so these unauthenticated **GET** routes — which carry no request body — pass straight through with no signature check. There is **no need to move, re-order, split, or re-scope** the existing middleware, and the new routes are explicitly **not** behind Discord signature verification. Do **not** add a JSON `POST` route to the dashboard router; if one ever becomes necessary, give it its own body parser without the Discord `verify` hook (or scope that hook to `/interactions` only) so it is not rejected with a 401. Depends on: steps 1–2.
   - **Decide what `/` serves** (see Decisions): recommended — let `express.static` serve `public/index.html` at `/`, and move the "IM ALIVE" liveness string to `GET /health` (so any Fly/Discord health check that hits `/` still gets a page, and there's still a plain-text liveness route). Depends on: steps 1–2.

Depends on: step 2 (endpoint contract), step 6 (utility classes available).

Numbered pagination is now preferred because App-UI ships a real, licensed component for it and it gives direct page access + a result count.

### Phase 3 — Tailwind build pipeline

6. **Install devDependencies (Tailwind v4):** `npm install -D tailwindcss @tailwindcss/postcss postcss` — **no `autoprefixer`** (v4 has vendor-prefixing + `@import` inlining built in). To run the PostCSS pipeline from an npm script, also add a runner, `postcss-cli`, so `build:css` can invoke `postcss` against `postcss.config.mjs`. (Single-package alternative: `@tailwindcss/cli`, but that bypasses `postcss.config.mjs`; prefer `postcss-cli` to keep the config file meaningful.) Parallelizable with Phase 1.

7. **Add config files (Tailwind v4):**

## Decisions (assumptions & scope boundaries)

1. **Same process, same `app.js`.** The bot is already an Express webhook server; the dashboard rides along in the same process. No separate server/script. (Strong recommendation — the alternative of a second process adds infra for no benefit here.)
2. **Achievements source = static catalog modules (paginated); Discord roles = live `GetGuildRoles(GUILD_ID)`** (with an icon-stripped static-catalog fallback + short cache). This matches how `handleViewAchievements` already sources data.
3. **Achievements are paginated (offset-based); icons are included per page.** The API accepts `page`/`pageSize` and returns `icon` only for the current page's slice, plus `pagination { page, pageSize, total, totalPages }`. **Offset-based (page/pageSize), not cursor-based**, because `ACHIEVEMENT_ROLES` is a *static, in-memory, fixed-order array of 33 entries* — it never grows or reorders at runtime, so the offset-drift problems that motivate cursors (items inserted/deleted between requests causing skipped/duplicated rows) cannot occur here. Slicing is a trivial `Array.prototype.slice` and `total` is `Array.length`; cursors would add opaque-token bookkeeping for zero benefit.
4. **Roles are returned in full and NOT paginated.** Live guild roles come from `GetGuildRoles`, which returns Discord role objects whose `icon` is a hash string/`null` (no base64), so the array is bounded by guild role count (tens) and weighs a few KB. Pagination exists solely to bound the achievement-**icon** payload; roles have no such payload, so paginating them would add endpoint/UI complexity for no bandwidth win. To avoid re-sending roles on every "load more" fetch, include `roles` only on `page=1`/absent (client fetches them once); returning them every request is an acceptable simpler alternative. The static-catalog fallback for roles strips `icon` so it stays small too.
5. **Tailwind v4** (CSS-first), PostCSS pipeline via `@tailwindcss/postcss` — `npm install -D tailwindcss @tailwindcss/postcss postcss` (no `autoprefixer`; v4 bundles vendor-prefixing + `@import` inlining), a `postcss.config.mjs` registering the `@tailwindcss/postcss` plugin, and an `input.css` whose first line is `@import "tailwindcss";` (replacing v3's three `@tailwind` directives). **v4, not v3, is required** because every chosen Tailwind Plus snippet is written in Tailwind **v4.3** markup (`size-*`, `text-sm/6`, `inset-ring`, `not-dark:*`, `outline -outline-offset-1`); compiling those against v3 would silently drop or mis-render them. A `tailwind.config.js` is optional/unused — config is CSS-first via an optional `@theme {…}` block, skipped here (the default gray/indigo palette matches the snippets).
6. **Real Tailwind Plus (Application UI) snippets are the source — not an approximated idiom.** Earlier there were no licensed snippets, so the look was to be approximated with plain utilities and a hand-built grid/pagination; now the purchased **Application UI** package supplies real, licensed components for every region, which are hand-copied/adapted into `public/index.html` / `public/app.js` (see sourcing section). This is permitted for internal/commercial use; only wholesale redistribution of the library is prohibited.
7. **`/` serves the homepage; liveness moves to `/health`.** Keeps a plain-text liveness route while giving `/` a real page.
8. **Public, unauthenticated endpoint.** The catalog and role list are treated as non-sensitive. No auth added. (Flag if the roles list should be gated.)
9. **CSS built during deploy (Docker `RUN npm run build:css`)** rather than committing generated output; `dist` stays gitignored.
10. **Default `pageSize = 12`** (→ 3 pages for 33 achievements), clamped to a max (e.g. 50). Chosen to keep each response modest while minimizing round-trips; adjustable without contract changes.
11. **Package: Application UI only; marketing-v4 dropped.** Both Tailwind Plus packages were downloaded, but the dashboard is built exclusively from `application-ui-v4/` because it is purpose-built for dashboard/app UI and supplies a licensed component for every region (shell, stats, grid list, stacked list, badges, pagination, empty state). App-UI has no `footers/` folder, but an internal bot-admin dashboard does not need a marketing footer — a one-line copyright `<footer>` in matching utilities covers it. Pulling marketing-v4 in just for a footer would mix two visual systems (landing-page scale vs. dense dashboard scale) and read inconsistently, so it is intentionally excluded. Per-region choices: shell `application-shells/stacked/01-with-bottom-border.html`; stats `data-display/stats/03-simple-in-cards.html`; grid `lists/grid-lists/06-images-with-details.html`; roles `lists/stacked-lists/17-narrow-with-badges.html` + `elements/badges/09-flat-pill.html`; pagination `navigation/pagination/01-card-footer-with-page-buttons.html`; optional empty state `feedback/empty-states/01-simple.html`; optional card wrapper `layout/cards/04-card-with-footer.html`.
12. **Numbered pagination is the default render strategy** (replacing the earlier "Load more" default), now that App-UI ships a real numbered-pagination component (`navigation/pagination/01-card-footer-with-page-buttons.html`). Each page click replaces the grid with the selected page and gives direct page access + a result count; the static anchors are adapted to JS click handlers with dynamically generated numbers/ellipsis, boundary-disabled Prev/Next, and an active-page state. "Load more" (append) remains a noted alternative on the same endpoint/contract.

## Further Considerations (open questions with recommendations)

- **Which "Discord roles"?** Default is *live guild roles* via `GetGuildRoles`. If you instead want only the *managed* role definitions (achievement + crafting + profession), we skip the Discord API call entirely and read the static modules — simpler and no token dependency. *Recommendation:* live guild roles, since that is "all Discord roles"; confirm if you'd prefer the managed-only set.
- **Snippet source is settled: Application UI (real Tailwind Plus), marketing-v4 dropped.** The purchased App-UI package supplies a licensed component per region (see sourcing section + Decision 11); marketing-v4 is intentionally not used to avoid mixing two visual systems, and its only unique offering here (a footer) is replaced by a one-line copyright `<footer>`. *Open only if:* you specifically want a richer marketing-style footer or hero band — then a single marketing-v4 footer (e.g. `sections/footers/14-simple-with-social-links.html`) could be layered in, accepting the minor visual-scale mismatch. *Recommendation:* App-UI only.
- **Icons on the page — handled via pagination.** Icons *are* shown; the paginated endpoint returns base64 `icon` URIs for the current page only, so the full ~4.3 MB set is never sent at once. *Open optimization (optional, not blocking):* a few source PNGs are oversized (one ~735 KB). If per-page weight still feels heavy, options are (a) shrink/re-encode the source PNGs, or (b) later move icons to a dedicated route (`GET /api/achievements/:custom_id/icon.png` decoding the base64) or pre-exported PNG files served statically with `Cache-Control`, so browsers cache them across page loads. *Recommendation:* ship base64-in-page-response first; do the icon-optimization/dedicated-route pass only if load times warrant it.
- **Move catalog to Mongo eventually?** Not needed for this feature — the static modules are already importable shared config. Only revisit if you want to edit achievements at runtime without a redeploy.
- **Health-check impact of repurposing `/`.** Confirm nothing external asserts on the exact `/` "IM ALIVE" string before moving it to `/health`.
